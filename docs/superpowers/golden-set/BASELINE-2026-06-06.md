# Golden-set — BASELINE (2026-06-06)

Regression oracle for the cargo↔vessel matching engine. 15 records, every one externally
verified by Opus 20-year-broker sessions (full provenance + double-compute TCE in
`verified-pairs.json`, matched by `id`). Run: `npm run golden`.

## Result: 69/69 tests pass · 4/4 suites green

- **4 good controls** (green belt — must stay profitable / `tceSign positive`):
  sugar panamax ~$22.5k · manganese panamax ~$15k · coal supramax ~$8.5k · olive-pomace handysize ~$10.75k.
- **11 bug pairs** — gate assertions. The live engine (`analyzePairs`) already enforces most,
  so those assert as green `it`. **Only 3 gates are still unfixed** (`it.failing`, red now,
  auto-flip green when a fix lands).

## The headline finding

The **live engine is much better than the old board implied.** `data/demo-seed.db` (425 matches,
the discovery board) surfaced restriction / laycan / capacity / spot pairs with fat TCE — but
that board was built through a different (build-pipeline) path. Run against the LIVE
`analyzePairs`, the engine **already**:

- BLOCKS trading-restriction violations (BARABULKA no-UA/EU; SNAPPER no-EU) → bucket `blocked`.
- BLOCKS laycan-infeasible pairs (PANTHERA-J open Continent vs 20-May laycan; FAITH Brazil-ballast;
  O7-GAJA prompt-miss) → `blocked`.
- BLOCKS capacity overflow (10,400 mt HRC vs PANTHERA-J 7,000 DWT) → `blocked`.
- Does NOT main-bucket a spot/no-position vessel (LADY ANITA) or a below-OPEX long-ballast pair
  (GLORY TOM × Kandla).
- Computes a NEGATIVE TCE for the under-utilised weight-range salt pair.

So the golden-set's first job is done: it proves the engine's gates work on the live path, and
it pins down exactly what's left.

| `GS-shortleg-tce`     | `verdict` | ranks a 5–10k parcel on a 30k-DWT handymax (17–33% util, short leg) as a scored match             | penalise tiny-parcel/low-util voyages so true-voyage TCE < OPEX is not surfaced as good |

A 4th systematic issue is documented but **not yet asserted tightly** (see Known limitations):
the engine often uses the **ballast/short leg as the voyage distance**, inflating TCE 2.5–6×
(e.g. Douala salt: engine $27,564/day on the 1,897 nm ballast leg vs ~$10k on the real ~4,900 nm laden).

## How the oracle works (so a future fix auto-detects)

- **Generic** `weight` / `distance` / `tce` tests = computability + WIDE bands only (the engine's
  TCE magnitude is a known mirage; we don't assert it yet).
- **`engineMust` gate flags** = the real oracle. A gate the engine already enforces → green `it`.
  A gate still unfixed is listed in the record's **`xfail`** array → `it.failing`. When the engine
  gains the gate, the `it.failing` starts PASSING → Jest flags "failing test passed" → you delete
  the key from `xfail` and it becomes a permanent green guard. No fixture rewrite needed.
- **Controls** assert `tceSign positive` (the one thing the engine gets right for profitable pairs).

## Known limitations (v1 → tighten later)

1. **Distance band is ±90%** (computability), so engine mis-routing (e.g. manganese Cape 14,772 nm
   vs engine 3,009 nm) is NOT caught yet. Tighten to ±3–5% vs external once the engine's
   laden-leg selection is fixed — that tightening is itself the regression test for the
   ballast-leg-as-distance bug.
2. **TCE magnitude is not asserted** (band is effectively infinite) for the same reason. Once the
   engine computes true-voyage TCE, re-peg `expected.tcePerDay` to the broker centrals in
   `verified-pairs.json` with a real ±% band.
3. **`weightNotMax`** (range priced at max) is recorded as a flag but has no driver assertion yet
   (no engine signal exposed); the weight-range loss IS caught via `tceSign negative`.
4. The demo-seed board path that produced the fat-TCE mirages is NOT exercised here — the golden-set
   tests `analyzePairs` directly. If the board/build path diverges from `analyzePairs`, that's a
   separate wiring audit.
