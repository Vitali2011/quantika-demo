## The 2 remaining gaps (it.failing — the engine roadmap)

Both share ONE root cause: **the engine's TCE omits the ballast reposition leg** (open position →
load port). `computeEstimatedTce`/`calculateTCE` (`lib/matching/tce-calculator.ts` →
`lib/economics/voyage-calculator.ts`) count only the laden leg's days + bunkers; the ballast leg is
used ONLY for the war-risk premium, never for voyage days/cost. So a long unpaid reposition or a
tiny-parcel/short-leg voyage never drags the daily TCE down.

| Record             | Gap (key) | What the engine does today                                                                             | Fix flips it green                                                     |
| ------------------ | --------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `GS-shortleg-tce`  | `verdict` | ranks a 5–10k parcel on a 30k-DWT handymax (17–33% util, short leg) as a scored match in the main list | true-voyage (ballast-incl.) TCE < OPEX → bucket out of `main`/`review` |
| `GS-negtce-laycan` | `tceNeg`  | blocks on laycan (✓) but the computed TCE is not negative for the 13-day-ballast 7kt parcel            | true-voyage TCE incl. ballast reposition → negative                    |

So the remaining engine work is essentially ONE change: **make `buildMatchEconomics` compute a
true-voyage TCE that includes the ballast leg** (open→load distance at ballast speed/consumption),
then let the realism partition bucket below-OPEX pairs. This is a CORE-ECONOMICS change — it shifts
every main-match TCE downward — so it carries real regression risk (matching has a regression
history) and needs a full `lib/matching` + `lib/economics` suite run, not a drive-by edit. It also
fixes the **ballast-leg-as-distance inflation** seen on the discovery board (Douala salt $27,564/day
on the 1,897 nm ballast leg vs ~$10k on the real ~4,900 nm laden).

## How the oracle works (so a future fix auto-detects)

- **Generic** `weight` / `distance` / `tce` tests = computability + WIDE bands only (the engine's
  TCE magnitude is a known mirage; we don't assert it yet).
- **`engineMust` gate flags** = the real oracle. A gate the engine already enforces → green `it`.
  A gate still unfixed is listed in the record's **`xfail`** array → `it.failing`. When the engine
  gains the gate, the `it.failing` starts PASSING → Jest flags "failing test passed" → you delete
  the key from `xfail` and it becomes a permanent green guard. No fixture rewrite needed.
- **Controls** assert `tceSign positive` (the one thing the engine gets right for profitable pairs).

## Known limitations (v1 → tighten later)

1. **Distance band is ±90%** (computability), so engine mis-routing (e.g. manganese Cape 14,772 nm
   vs engine 3,009 nm) is NOT caught yet. Tighten to ±3–5% vs external once the engine's
   laden-leg selection is fixed — that tightening is itself the regression test for the
   ballast-leg-as-distance bug.
2. **TCE magnitude is not asserted** (band is effectively infinite) for the same reason. Once the
   engine computes true-voyage TCE, re-peg `expected.tcePerDay` to the broker centrals in
   `verified-pairs.json` with a real ±% band.
3. **`weightNotMax`** (range priced at max) is recorded as a flag but has no driver assertion yet
   (no engine signal exposed); the weight-range loss IS caught via `tceSign negative`.
4. The demo-seed board path that produced the fat-TCE mirages is NOT exercised here — the golden-set
   tests `analyzePairs` directly. If the board/build path diverges from `analyzePairs`, that's a
   separate wiring audit.
