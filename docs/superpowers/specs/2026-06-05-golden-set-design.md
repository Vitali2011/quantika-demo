# Golden-Set (эталонный набор матчей) — дизайн

> Дата: 2026-06-05. Фаза 2 ремонта матчинга (после v4.0 orchestrator-day rebuild).
> Связано: `docs/RETROSPECTIVE-root-cause-2026-06-05.md` (корень багов),
> `docs/BUGFIX-WAVES-2026-06-05.md` (триаж W0–W5), VALUE_CHECK / Check F
> (`scripts/pre-merge-check.sh` в репо скила orchestrator-day).

## Зачем (одной фразой)

У системы **нет способа узнать, что она ошибается**. Все гейты мерят «запускается / тесты
зелёные / страница рисуется», но ни один не спрашивает «эти $34,870 ПРАВДА верны для этого
судна?». Golden-set — это тот **оракул**, которого не было: 20 пар «судно × груз» с вручную
выверенными числами (TCE, дистанция, вес), против которых сверяется любой прогон движка.

Две роли:

1. **Регрессионный оракул для VALUE_CHECK** — матчинг-PR не мержится, пока golden-числа не
   сошлись (Check F, exit 4).
2. **Образец-шаблон для ремонта прода** — каждый matching-баг получает свою эталонную пару;
   фикс виден как красное→зелёное на уровне _числа_, а не «тесты прошли».

## Что это (определение)

Версионируемый файл-фикстура в репо + тест, который гоняет **сам движок** на входах каждого
эталона и сверяет три числа (+ флаги честности) с выверенной правдой. НЕ читает сохранённую
БД (она бывает stale — «stored, не recompute»), а пересчитывает заново.

## Три решения (приняты на брейнсторме 2026-06-05)

1. **Высота = ГИБРИД.** Golden-число берётся из РЕАЛЬНЫХ входов где они есть; где входа нет —
   golden честно помечает «дефолт/оценка» и проверяет, что движок ТОЖЕ это показывает, а не
   выдаёт выдуманное за факт. Ловит и ошибки расчёта, и корень из ретроспективы (входы-заглушки).
2. **Доверие = ВНЕШНИЙ ИСТОЧНИК + ДВОЙНОЙ РАСЧЁТ.** Где число можно посмотреть — берём извне
   (независимо от движка). Где считается (TCE) — два независимых расчёта должны сойтись, иначе
   флаг. Экзаменатор ≠ студент: оракул не может быть тем же источником, что пишет баг.
3. **Отбор = БАТАРЕЯ ПОД БАГИ.** Каждая пара проверяет конкретный класс бага + 4–5 заведомо
   чистых контрольных пар. Фикс бага виден на своей паре.

## Откуда «правда» — пять входов

| Число             | Внешний источник (независим от движка)                              | Механика                                                                               |
| ----------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **вес**           | сырой текст письма груза (`.private/raw-emails/*.json`)             | агент/человек читает заявленное кол-во                                                 |
| **дистанция**     | **searoutes.com (веб)**                                             | НЕ локальный `searoute-pairs.json` — он = Tier-2 движка (шпаргалка студента, см. ниже) |
| **ставка фрахта** | заявлена в письме → берём её; иначе публичный индекс на frozen-дату | stated → index fallback                                                                |
| **бункер**        | публичная цена бункера на frozen-дату                               | web                                                                                    |
| **TCE**           | стандартная формула + **два независимых расчёта**                   | adversarial (см. ниже)                                                                 |

**Почему дистанция = веб, а не локальный JSON (проверено по коду):** движок резолвит
дистанцию тремя ярусами в `lib/sailing/port-distances.ts` — Tier-1 ручная матрица →
**Tier-2 `data/distances/searoute-pairs.json`** (строка 1267, `require(...)`) → Tier-3 живой
`searoute-client`. Локальный JSON — вход самого движка. Сверять им = сверять студента с его
шпаргалкой. Комментарий в коде (`port-distances.ts:1041`) сам отмечает, что searoute JSON
«unreliable (~40% under-estimate)» на части пар. → оракул = независимый веб-searoute.

## Двойной расчёт TCE (adversarial)

Стандартная отраслевая формула: `TCE/день = (валовый фрахт − комиссии − стоимость бункера −
портсборы) / общие судо-сутки рейса`. Входы берутся отдельно от движка (вес из письма,
дистанция из веба, расход из письма или класс-стандарт, бункер из публичной цены, портсборы
из DA-справки).

- **Расчёт A** и **расчёт B** — два независимых агента, разный метод/декомпозиция.
- Сходятся в пределах допуска TCE → golden-число = согласованное.
- Расходятся → **флаг фаундеру** (не авто-проход — это и есть защита от formatAge).
- Фаундер выборочно сверяет **3–4** TCE на брокерский нюх.

## Гибрид-флаг — «сделать отсутствие громким»

Прямая реализация рекомендации №2 из ретроспективы. Для каждого входа golden пишет, реальный
он или дефолт (`input_honesty`). Где дефолт — `engine_must.*_marked_est` требует, чтобы движок
показал «est./оценка», а не выдал заглушку (12.5 узла, 25т) за факт. Так выдуманное становится
видимым глазом и тестируемым.

## Состав батареи (~20 пар)

По одному эталону на класс бага (приоритет — баги матчинг-трека из BUGFIX-WAVES):

| #     | Класс бага                      | Что проверяет                                                                         | Ref       |
| ----- | ------------------------------- | ------------------------------------------------------------------------------------- | --------- |
| 1     | negative-TCE                    | убыток получает кап, не good                                                          | B4        |
| 2     | detectSpot object-openDate      | спот-судно не демоутится в idle                                                       | B10       |
| 3     | weight-range → max              | вес-диапазон → null, не верхняя граница                                               | B6        |
| 4     | Black Sea short-leg             | дистанция/портсборы≠$0/Tier-2 фрахт                                                   | B7        |
| 5     | unknown-port gate               | «null→pass» не пропускает плохой матч молча                                           | гейты     |
| 6     | list↔detail TCE                 | карточка == список (один TCE)                                                         | #819/B5   |
| 7     | absent-speed → est              | дефолт скорости помечен est., не факт                                                 | B3        |
| 8     | DWT 35–50k класс                | ultramax не считается как handysize                                                   | readiness |
| 9     | war-position HRA                | узкий гейт #784 на черноморских                                                       | #784      |
| 10    | part-cargo utilisation          | частичный груз не ломает util                                                         | util      |
| 11–15 | **контроль: чистые прибыльные** | фикс не ломает заведомо хорошие (handysize/supramax/panamax/clean-laycan/clean-route) | —         |
| 16–20 | резерв/расширение               | добор по находкам на сборке                                                           | —         |

Каждая пара = смысл. Фикс B10 → пара #2 краснеет→зеленеет на уровне числа.

## Допуски (решено, поправимо)

- **вес** — точно (`tolerance_abs: 0`); это заявленное в письме число.
- **дистанция** — `±3%` (разные роутинги дают мелкий разброс).
- **TCE** — `±$500/день ИЛИ ±5%`, что больше (узко → мигает зря; широко → пропустит дрейф).

## Как бежит (тест + интеграция)

- **Фикстура:** `lib/matching/__tests__/golden-set/golden-matches.json` (версионируется, в git).
- **Тест:** `lib/matching/__tests__/golden-set/golden-set.test.ts`:
  1. грузит фикстуру;
  2. инъектит замороженные часы = `frozen_date` (детерминизм дат/laycan);
  3. на каждый эталон строит cargo+vessel из `inputs`, гоняет **движок** (тот же путь, что
     `regenerate-matches` → `analyzePairs` + `buildMatchEconomics`, пустой aiScorer → sweep);
  4. сверяет `distance_nm`/`weight_t`/`tce_per_day` с допуском;
  5. проверяет все `engine_must.*` (включая `*_marked_est` для дефолт-входов).
- **VALUE_CHECK-плуг:** матчинг-PR (трогает движок/экономику) на pre-merge гоняет golden-тест.
  Прошёл → `value-check-emit.sh <pr> golden-set match golden`. Упал → `mismatch` → Check F BLOCK
  (exit 4). Это тот оракул, под который строился Check F в v4.0.

## Сборка — процесс и feasibility (проверено по земле)

Сырьё на месте локально (твой MacBook), строить можно без прода:

- `.private/raw-emails/` — **153 сырых письма** (Gmail-формат, с телами) → источник реальных входов.
- `.private/etms-corpus.json` (397 КБ) — корпус/манифест.
- `data/distances/searoute-pairs.json` — локальный словарь (= Tier-2 движка, НЕ оракул).
- `data/demo-seed.db` — **0 байт** (собирается через `build.ts`); `sessions.db` — matches = 0.

**Процесс сборки:**

1. Прогнать движок локально на парах из корпуса → найти текущие выходы → отобрать эталон под
   каждый класс бага (где движок сейчас врёт — берём как красную пару; где честен — контроль).
2. Для каждой пары: вес из письма, дистанция с searoutes.com (веб), фрахт/бункер из источников,
   TCE двойным расчётом.
3. Записать фикстуру + написать тест.
4. Прогнать тест на текущем main: красные пары (баги ещё не чинены) — ожидаемо красные;
   контрольные — зелёные. Это и есть «оракул до ремонта».

Это **основная работа сессии** — 20 пар с двойным расчётом строятся не за пять минут.

## Риски и открытые вопросы

- **Entry-point движка** для теста — `analyzePairs` + `buildMatchEconomics`; точную сигнатуру
  пиннит план (как вызывает `regenerate-matches.ts`).
- **Замороженные часы в тесте** — нужно инъектить `now()`/clock так же, как demo (через
  ClockProvider / `lib/clock.ts`), иначе даты поедут. План определит механику инъекции.
- **Веб-доступ к searoutes.com** на сборке — если недоступен, fallback: sea-distances.org или
  ручная сверка фаундером. Записывается в `provenance`.
- **frozen_date** — пиннится в фикстуре на сборке (из контекста выбранных пар), не хардкод сейчас.
- **Часть входов физически отсутствует** в письмах — это НЕ дефект набора, а смысл гибрида:
  такие пары идут с `DEFAULT`-флагом и проверяют, что движок честно помечает est.

## Вне scope

- **Сам ремонт matching-багов** (B3/B4/B5/B6/B7/B8/B10/B16/B19) — golden-set это ОРАКУЛ, а не фикс.
  Фиксы идут отдельными волнами W2–W4, сверяясь об этот набор.
- **Не-матчинговые баги** (UI/сессии/конфиг/security) — отдельная orchestrator-сессия
  (`docs/superpowers/plans/2026-06-05-non-matching-parallel-waves.md`).
- **fit% / score reconciliation** — не входит в три числа набора (можно добавить позже отдельным
  классом, но сейчас держим TCE/дистанцию/вес).
