## Problem

War-risk premium (`lib/economics/war-risk.ts`) is **arithmetically correct for the
port-keyword case** (Berbera verified) but rests on three holes:

- **Д1 — stale hardcoded rates.** `red-sea-hra.premiumPercentPerTransit = 0.00075`
  (0.075%) @ `JWC_RATE_DATE = '2024-01-01'` — **880 days stale**. Knowledge YAML
  `data/knowledge/jwc/2025-current.yaml` (bulletin JWLA-033, effective 2026-03-12)
  carries Red Sea **0.20%** (post-Houthi-ceasefire). Calc **understates hull premium
  ~2.7×** on Red Sea routes.
- **Д2 — two sources of truth, no sync.** `war_risk_zones` DB (migration 016, fed
  from YAML via `lib/knowledge/jwc/adapter.ts`) feeds **only** knowledge/RAG. The
  TCE calc sits on hardcoded `JWC_HRA_ZONES`. The two diverge silently (e.g.
  `BGBURGAS` in YAML black-sea, absent in TS).
- **Д3 — `viaCanal` not threaded.** `tce-calculator.ts:366-369` calls
  `calculateWarRiskPremium` with `{ fromPort, toPort }` only — **no `viaCanal`**.
  A Suez-transit voyage to a **non-HRA** port yields **$0** war-risk (false
  negative). `_routeTransitsSuez()` already exists (`tce-calculator.ts:189`) and is
  already computed at `:309`, but is consumed **only** for canal fees.

## Goal

1. Calc reads **live JWC rates** from the knowledge source (single source of truth),
   **staleness-aware** (circular date visible), **fallback** to hardcoded when the
   knowledge source is unavailable.
2. **Suez transit** (via `_routeTransitsSuez` basin classification) triggers
   `red-sea-hra` even **without** an HRA port — thread `viaCanal`.
3. **Mandatory final exec stage:** war-risk **shift-table** (old vs new, by route)
   over prod matches to the founder **before merge** — value-bearing (hull ×2.7 on
   Red Sea), like the L2 flip-sign table and `#stage9-value-shift`.

## Out of scope

- **No** changes to the knowledge ingest path (parser zod schema, migration 016
  `NOT NULL`, `adapter.ts` upsert). `2025-current.yaml` has `null` transit/hold
  rates (libya, cabo-delgado) that the current zod schema *rejects* — touching that
  expands scope into knowledge/RAG regression surface. The economics rate-loader
  parses the YAML **tolerantly and independently** (skips null-rate zones).
- **No** hold-rate / at-anchor modelling. v2 is per-transit hull only (unchanged
  model). hold_rate_pct ignored.
- **No** Hormuz sub-zone split, no flag-based multipliers, no live underwriter
  quote integration. Documented as future.
- **No** live-LLM runs on dev (dev-LLM dead, billing). Shift-table is a pure
  economics recompute over stored matches — no LLM required.

## Design

### A. Live-rate loader — `lib/economics/war-risk-rates.ts` (NEW)

A self-contained, **synchronous**, memoized loader living inside `lib/economics`
(no heavy knowledge imports). Reads the JWC YAML directly with `readFileSync` +
`yaml.parse`, tolerant of `null` rates.

```
loadJwcRates(yamlPath = 'data/knowledge/jwc/2025-current.yaml'):
  { byCalcZoneId: Record<string, number>, effectiveFrom: string, version: string, source: 'knowledge' }
  | null  (on any error / missing file)
```

- **Tolerant parse:** skip zones where `transit_rate_pct == null` (libya,
  cabo-delgado). Do **not** reuse `lib/knowledge/jwc/parser.ts` (its zod rejects
  null). Minimal inline validation: finite, `0 <= pct <= 10`.
- **Unit conversion:** YAML `transit_rate_pct` is in **percent** (`0.20` = 0.20%);
  calc wants a fraction → `premiumPercentPerTransit = transit_rate_pct / 100`
  (`0.20 → 0.002`).
- **Zone-id mapping** (calc zone → knowledge zone), explicit const table — the IDs
  do **not** match 1:1:

  | calc zone id (`JWC_HRA_ZONES`) | knowledge `zone_id` (YAML) | JWLA-033 transit % |
  |---|---|---|
  | `red-sea-hra` | `red-sea` | 0.20 |
  | `gulf-of-guinea` | `gulf-of-guinea` | 0.50 |
  | `black-sea-hra` | `black-sea` | 0.65 |
  | `persian-gulf-hra` | `persian-gulf-oman-indian-ocean` | 0.75 |
  | `indian-ocean-hra` | `persian-gulf-oman-indian-ocean` (JWLA-033 merged Indian Ocean in) | 0.75 |

  `strait-of-hormuz` (2.25%) is **not** mapped in v2 (no calc sub-zone) — noted as
  future. A calc zone with no knowledge mapping (none currently) → keep its
  hardcoded rate.
- **Memoize** at module scope (calc is per-match hot path): parse once, cache the
  result + a `null` sentinel on failure so we don't re-`readFileSync` every call.
  Expose `__resetRateCacheForTest()` for deterministic tests.
- **Staleness:** return `effectiveFrom` (`2026-03-12`) so it flows into
  `WarRiskResult.rateDate` (replaces the `'2024-01-01'` constant when live rates
  load). W6a badge (`CalculationWaterfall.tsx`) then shows the **real** circular
  date — stale-but-honest becomes fresh-and-honest.

### B. `calculateWarRiskPremium` reads live rate per dominant zone

In `lib/economics/war-risk.ts`:

- After choosing `dominantZone`, resolve its **effective rate**:
  `rates = loadJwcRates(); rate = rates?.byCalcZoneId[dominantZone.id] ?? dominantZone.premiumPercentPerTransit`.
- `rateDate = rates ? rates.effectiveFrom : JWC_RATE_DATE` (fallback keeps the old
  constant for the no-knowledge case).
- Keep `JWC_HRA_ZONES` rates as the **fallback values** (do not delete — they are
  the documented degraded-mode rates; grep-guarded below).
- Add `rateSource: 'knowledge' | 'hardcoded'` to `WarRiskResult` so the UI/telemetry
  can show provenance (additive, optional field — no BC break).
- `PI_SURCHARGE_BY_ZONE_ID`, crew bonus — unchanged (not in YAML; keep hardcoded).

> **Why not read `war_risk_zones` DB?** The DB is populated from `2025-Q1.yaml` via
> the adapter, *not* `2025-current.yaml`, and migration 016 is `NOT NULL` so it
> can't even hold the current bulletin's null-rate zones. Reading the canonical
> **current** YAML directly is fresher, lower-risk, and keeps economics decoupled
> from the knowledge DB lifecycle. DB-as-source is a documented future option once
> the ingest path is migrated to `2025-current.yaml`.

### C. Thread `viaCanal` (Д3) — `tce-calculator.ts`

`ladenTransitsSuez` is already computed at `:309`. Thread it:

```ts
const warLaden = calculateWarRiskPremium({
  route: {
    fromPort: input.loadPort ?? '',
    toPort: input.dischargePort ?? '',
    viaCanal: ladenTransitsSuez ? 'suez' : undefined,   // NEW
  },
  vesselValueUsd: input.vesselValueUsd ?? estimateVesselValueUsd(safeDwt),
});
```

Ballast leg: compute `ballastTransitsSuez = _routeTransitsSuez(openPos, input.loadPort)`
(already computed at `:320` inside the `canalUsd` block — lift it to a `const` so
both the fee and the war-risk call reuse it) and thread `viaCanal` into `warBallast`
identically.

Effect: a Med↔East-of-Suez voyage now matches `red-sea-hra` via the `canals:['suez']`
branch even when neither endpoint is an HRA keyword port. **This is the
false-negative fix — and the largest behavioural shift; it expands war-risk
applicability to all Suez-transit routes.** Captured in the shift-table (§ Stage 5)
and the PI3 table below.

- Script: `scripts/diag/war-risk-shift-table.ts` (diag, not shipped).

    (a) hardcoded rates + no-viaCanal (OLD) and (b) live rates + viaCanal (NEW).

    OLD total / NEW total, Δ, **trigger reason** (port-keyword vs new-Suez-canal).

  value-bearing sign-off, exactly like the laden-draft flip-sign-off (#946).
- Dev-safe: no live LLM, only stored economics + deterministic recompute.

## Risks & mitigations

- **Suez-transit over-trigger.** Threading `viaCanal` makes *every* Med↔East-of-Suez
  voyage war-risk-applicable. Some may be commercially debatable (transit without
  Red-Sea call). → Surfaced in the shift-table for founder review; `red-sea-hra`
  canal match is the JWC-correct default (transit through Bab-el-Mandeb HRA).
  Mitigation lever if founder rejects: gate the canal-branch behind a flag — but
  default ON (false-negative fix is the goal).
- **YAML drift / missing file on prod.** Loader returns `null` → hardcoded fallback,
  no throw, no crash. Staleness badge then correctly shows old date.
- **Hot-path `readFileSync`.** Memoized once per process; negligible.
- **Knowledge/RAG untouched.** By deliberately *not* routing through parser/migration,
  zero risk to the retriever invariants (`.claude/rules/retriever.md`).
