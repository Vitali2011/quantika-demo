# Post-Deploy Smoke — t60 Bake Window Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> Before using Next.js/React APIs introduced or changed after v14 — WebFetch the relevant nextjs.org/react.dev docs page first. (This plan touches no Next.js/React APIs — only bash + GH workflow + the existing `smoke.mjs`.)

**Goal:** After the immediate post-deploy smoke PASSes, schedule a delayed re-run 60 minutes later on dev-vps (a "bake window"), producing `summary-t60.json` next to the immediate `summary.json`, so slow-burn regressions (memory leaks, cache warmup, cron side-effects) are caught after prod has been live for an hour.

**Architecture:** The 60-minute wait runs on **dev-vps via `systemd-run --on-active=60min`**, never as a `sleep` inside the GitHub runner (that would burn Actions minutes for a whole idle hour). The immediate smoke workflow, on PASS, SSHes into dev-vps and (a) records the just-deployed SHA into a dev-vps-local marker file and (b) schedules a fixed-name transient systemd timer. At t60 the timer fires `run-t60.sh`, which first checks whether prod has since moved to a newer SHA — if so it writes `overall=superseded` (a neutral verdict, not a failure), otherwise it **reuses the existing `smoke.mjs` unchanged** and writes its verdict to `summary-t60.json`. A new deploy replaces the earlier timer (same unit name) so only the newest bake window survives. The orchestrator does the prod-log comparison itself; this repo only owns the t60 *run*.

**Tech Stack:** bash, systemd transient units (`systemd-run`, `--on-active`, `--unit`, `--collect`), Playwright `smoke.mjs` (unchanged), GitHub Actions (`post-deploy-smoke.yml`), `jq`.

## Key Design Decisions

1. **Why dev-vps `systemd-run`, not a GH `sleep`.** A `sleep 3600` in the runner bills 60 Actions minutes per deploy for pure idle. `systemd-run --on-active=60min` schedules a transient timer on dev-vps (which already hosts `smoke.mjs` + chromium) and the runner exits immediately. Zero idle Actions minutes.

2. **Superseded detection is dev-vps-local, not a prod endpoint.** `/api/health` (see `app/api/health/route.ts`) exposes only a static `version`, **no commit SHA** — so t60 cannot ask prod "what SHA are you." Instead each `schedule-t60.sh` overwrites a single global marker file `.deployed-sha` with the SHA it is scheduling for. The scheduled SHA is also baked into the timer's command line (arg to `run-t60.sh`). At t60, `run-t60.sh` compares its own scheduled SHA against the current `.deployed-sha`; a mismatch means a newer deploy overwrote the marker → `superseded`. No prod SSH, no health-route change.

3. **Same-name unit = replace (constraint 2).** The timer uses a **fixed** unit name `quantika-t60-smoke`. A new deploy's `schedule-t60.sh` stops the old timer before creating the new one, so a stale bake window is cancelled — normally it never fires. The SHA guard in decision #2 is defense-in-depth for the narrow race where the old timer fires during the stop→recreate gap.

4. **Reuse `smoke.mjs` verbatim (constraint 4).** `run-t60.sh` invokes the same `node smoke.mjs`, capturing its stdout JSON (`smoke.mjs` reserves stdout for the summary — confirmed in its header comment). It points `SMOKE_OUTDIR` at a `t60/` subdir so `smoke.mjs`'s own `summary.json` + screenshots land there and never clobber the immediate run's `summary.json`. `run-t60.sh` then augments the captured JSON with `bake_window`/`scheduled_sha`/`superseded` and writes it as `summary-t60.json` **next to** `summary.json`. No `smoke.mjs` edits, no route-list duplication.

5. **Orchestrator owns the comparison (constraint 3).** This repo produces `summary-t60.json` only. Comparing it against `summary.json` / prod logs is the orchestrator's job, done outside this repo.

```bash
#!/usr/bin/env bash
# run-t60.sh — t60 bake-window re-run for quantika-demo post-deploy smoke.
# Runs on dev-vps, fired by a systemd transient timer 60 min after a PASS immediate smoke.
# Usage:  run-t60.sh <pr#> <scheduled-sha> [base-url]
# Output: ~/orchestrator-state/quantika-demo/post-deploy-checks/<pr#>/summary-t60.json
# Verdict (overall): PASS | FAIL | superseded
#   superseded = a newer deploy overwrote .deployed-sha before this bake window fired.

set -o pipefail
PR="${1:?Usage: run-t60.sh <pr#> <scheduled-sha> [base-url]}"
SHA="${2:?scheduled SHA required}"
BASE="${3:-https://demo.quantika.org}"

ROOT="$HOME/orchestrator-state/quantika-demo/post-deploy-checks"
PRDIR="$ROOT/$PR"
OUT="$PRDIR/summary-t60.json"
mkdir -p "$PRDIR"

CURRENT="$(cat "$ROOT/.deployed-sha" 2>/dev/null || echo '')"

# Superseded: prod has moved to a newer deploy since this bake window was scheduled.
if [ -n "$CURRENT" ] && [ "$SHA" != "$CURRENT" ]; then
  jq -n --arg pr "$PR" --arg sched "$SHA" --arg cur "$CURRENT" --arg base "$BASE" \
    '{pr:$pr, base_url:$base, bake_window:"t60", overall:"superseded",
      superseded:true, scheduled_sha:$sched, current_sha:$cur,
      reason:"newer deploy landed before t60 fired"}' > "$OUT"
  echo "=== t60 SUPERSEDED · PR #$PR · scheduled=$SHA current=$CURRENT ==="
  exit 0
fi

# Not superseded → reuse smoke.mjs unchanged. Its stdout is the JSON summary; point
# SMOKE_OUTDIR at a t60/ subdir so its own summary.json + screenshots don't clobber
# the immediate run's summary.json.
cd /root/post-deploy-smoke || exit 1
T60OUT="$PRDIR/t60"
mkdir -p "$T60OUT"
RAW="$(mktemp)"
SMOKE_PR="$PR" SMOKE_BASE_URL="$BASE" SMOKE_OUTDIR="$T60OUT" \
  node smoke.mjs > "$RAW" 2> "$PRDIR/t60-stderr.log"
RC=$?

# Augment the captured summary with bake-window metadata, write next to summary.json.
if jq empty "$RAW" 2>/dev/null; then
  jq --arg sched "$SHA" \
     '. + {bake_window:"t60", superseded:false, scheduled_sha:$sched}' "$RAW" > "$OUT"
else
  jq -n --arg pr "$PR" --arg sched "$SHA" \
    '{pr:$pr, bake_window:"t60", overall:"FAIL", superseded:false,
      scheduled_sha:$sched, reason:"smoke.mjs produced no valid JSON"}' > "$OUT"
  RC=1
fi
rm -f "$RAW"

echo "=== t60 SMOKE · PR #$PR · $BASE ==="
jq -r '"overall=" + .overall + "  scheduled_sha=" + .scheduled_sha' "$OUT" 2>/dev/null || cat "$OUT"
exit $RC
```

```bash
#!/usr/bin/env bash
# schedule-t60.sh — schedule the t60 bake-window re-run on dev-vps.
# Runs on dev-vps, invoked over SSH by post-deploy-smoke.yml after a PASS immediate smoke.
# Usage:  schedule-t60.sh <pr#> <sha> [base-url]
# Effect: records <sha> as the newest deploy, then (re)schedules a fixed-name transient
#         systemd timer to fire run-t60.sh 60 min from now. Same unit name => new deploy
#         replaces any earlier pending bake window.

set -o pipefail
PR="${1:?Usage: schedule-t60.sh <pr#> <sha> [base-url]}"
SHA="${2:?sha required}"
BASE="${3:-https://demo.quantika.org}"

UNIT="quantika-t60-smoke"
ROOT="$HOME/orchestrator-state/quantika-demo/post-deploy-checks"
PRDIR="$ROOT/$PR"
mkdir -p "$PRDIR"

# Record the just-deployed SHA: global marker (superseded source-of-truth) + per-PR copy.
echo "$SHA" > "$ROOT/.deployed-sha"
echo "$SHA" > "$PRDIR/t60-scheduled-sha"

# Replace any pending bake window: stop old timer/service, clear failed state, so the
# fresh systemd-run can claim the fixed unit name. --collect GCs a prior failed unit.
systemctl stop "$UNIT.timer" 2>/dev/null || true
systemctl stop "$UNIT.service" 2>/dev/null || true
systemctl reset-failed "$UNIT.service" 2>/dev/null || true

# Schedule the delayed run. --on-active=60min => fire 60 min from now, on dev-vps,
# runner exits immediately (no Actions minutes burned on the wait).
systemd-run \
  --unit="$UNIT" \
  --collect \
  --on-active=60min \
  --description="quantika-demo post-deploy t60 bake window (PR #$PR, $SHA)" \
  /root/post-deploy-smoke/run-t60.sh "$PR" "$SHA" "$BASE"

echo "=== t60 SCHEDULED · PR #$PR · sha=$SHA · fires in 60min (unit=$UNIT) ==="
```

**Claim to verify (orchestrator, ~75 min after this PR deploys to prod):**

> On dev-vps, the file
> `~/orchestrator-state/quantika-demo/post-deploy-checks/<PR>/summary-t60.json`
> exists and its `.overall` is **`PASS`** (bake window ran clean) **or** **`superseded`**
> (a newer deploy replaced this bake window before it fired). It must **not** be
> `FAIL` for a healthy prod, and it must **not** be absent.

**How to check (single command on dev-vps):**

```bash
jq -r '.overall' ~/orchestrator-state/quantika-demo/post-deploy-checks/<PR>/summary-t60.json
# expect: PASS   (or: superseded)
```

**Why 75 min, not 60:** the timer fires at deploy-time + 60 min; `run-t60.sh` then polls `/api/health` (up to 90 s) + walks 5 routes with retries (~1–3 min). A 75-min probe window clears the fire time plus the run. If the file is still absent at 75 min, inspect the timer: `systemctl status quantika-t60-smoke.timer` and `journalctl -u quantika-t60-smoke`.

**Superseded is a PASS-equivalent for this probe:** if the orchestrator deployed again within the hour, `superseded` is the *correct* verdict, not a regression — the newer deploy has (or will have) its own immediate smoke + its own bake window.
