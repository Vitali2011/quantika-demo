# Migration Robustness Audit — 2026-05-28

This audit covers the better-sqlite3 migration stack (40 migrations under `lib/migrations/`, applied by `lib/migrations/runner.ts` via the lazy `getStore()` → `new SessionStore()` path). Across 19 confirmed findings: 1 HIGH, 9 MED, 6 LOW (plus 3 confirmed-safe items retained for traceability). The single biggest risk is that the documented primary deploy (`scripts/deploy-vps.sh`) runs its only eager migrate step against a hardcoded `data/sessions.db` while the demo runtime serves `data/demo-seed.db`, so the served DB is never eagerly migrated and ships one migration behind on every deploy — leaving a clean deploy dependent on a fragile, error-swallowing lazy-apply path.

## CRITICAL — data-loss / silent-skip
_none_

## HIGH — non-idempotent / race

### deploy-vps.sh eager migrate targets the wrong database in demo mode
- **File:** scripts/deploy-vps.sh:32 — **Scenario:** The only eager migration trigger is `SESSIONS_DB_PATH=data/sessions.db npx tsx scripts/seed-port-da.ts`, whose `main()` calls `runMigrations(db, allMigrations)` against `data/sessions.db`. But `.env.demo` sets `SESSIONS_DB_PATH=data/demo-seed.db` (+`DEMO_MODE=true`), so the demo server reads/migrates `data/demo-seed.db` (via `getStore()` → `DEFAULT_DB_PATH`), while the deploy migrated an unrelated throwaway DB. The deploy's "migrations applied OK" signal is from the wrong file; the served demo DB is left to the lazy first-request path. — **Repro:** (1) `deploy-vps.sh:13 git reset --hard origin/main` restores the git-tracked `data/demo-seed.db`, verified at `MAX(version)=39, COUNT=39` while 40 migration files exist (040-counter-offers not applied) — the served DB ships exactly one migration behind on every deploy. (2) Line 32 migrates the gitignored throwaway `data/sessions.db` to v40. (3) `pm2 restart --update-env` boots with `SESSIONS_DB_PATH=data/demo-seed.db`. (4) `curl /api/health` (line 40) → `getSessionCount` → `getStore` → `new SessionStore` → `runMigrations` against `data/demo-seed.db` — only HERE does 040 finally apply, lazily. (5) `deploy-vps.sh` never invokes `scripts/ops/verify-deploy.sh`, so the `MAX(version) != file-count` gate never runs (and verify-deploy.sh:22 itself hardcodes `DB_PATH=data/sessions.db`, so it would check the wrong DB anyway). — **Fix:** Do not hardcode the DB path; source the runtime env so the seed/migrate step uses the same `SESSIONS_DB_PATH` the server will (`set -a; . ./.env.local; set +a; npx tsx scripts/seed-port-da.ts`). Run `scripts/ops/verify-deploy.sh` after restart (and fix its hardcoded `DB_PATH`) so a `MAX(version) != migration-file-count` mismatch aborts the deploy.

## MED — ordering / race / drift / destructive / idempotency

### Pending migration can stay unapplied while traffic is served; root-layout getStore() construction is wrapped in error-swallowing catch{}
- **File:** app/layout.tsx:120 (also :56) — **Scenario:** Migrations are lazy, so the app can serve traffic before any pending migration applies. In `app/layout.tsx` both `getStore()` touches (`resolveInitialMode` at :56 and the RootLayout body at :120) sit inside `try { const db = getStore().getDatabase(); ... SELECT preferred_mode FROM user_preferences ... } catch { }`. The migration-bearing `new SessionStore()` runs as a side-effect of the first successful `getStore()`. If that construction throws mid-migration, the throw is swallowed by the best-effort catch, `_store` stays null, and the page renders HTTP 200 with default (charterer) mode — masking a stale/failed schema as silently-degraded UI instead of a loud 500. — **Repro:** Fresh `data/sessions.db` (no `_store` yet) plus a construction-throwing condition (realistic trigger: sqlite-vec fails to load so migration 018/029 `CREATE VIRTUAL TABLE ... USING vec0` throws — the documented vec0 prod-failure class; the `SessionStore` constructor has no internal try/catch, verified lib/session-store.ts:38-89). (1) `instrumentation.register()` runs no `getStore()` — no eager migrate. (2) First authenticated request renders RootLayout → line 118 else-if. (3) Line 120 `getStore()` → `_store = new SessionStore()` → `runMigrations` → a migration `up()` throws; earlier committed migrations stay, the failing one rolls back, `_store` stays null. (4) Throw propagates into the try and is swallowed at the `catch`; `initialMode` stays charterer, HTTP 200. (5) Every subsequent request re-enters the null-`_store` constructor and re-throws/re-swallows → persistent degraded UI (mode forced to charterer, missing KPIs) with no surfaced error. — **Fix:** Make migration apply eager at boot so schema is current before first request; instantiate the store (run migrations) in a dedicated fail-loud boot path, and keep the catch{} only around the actual SELECT, not around store construction.

### Lazy concurrent runMigrations have no WAL and no busy_timeout — concurrent first-requests can hit SQLITE_BUSY / partial apply
- **File:** lib/session-store.ts:40 (also lib/db/index.ts:18) — **Scenario:** Neither `getDb()` (lib/db/index.ts:17-21) nor the `SessionStore` constructor (lib/session-store.ts:40-48) sets `journal_mode=WAL` or `busy_timeout`; only `foreign_keys=ON` is set (line 46). better-sqlite3 then defaults to rollback journal with `busy_timeout=0` (immediate SQLITE_BUSY). pm2 is `instances:1` (fork mode), but many OTHER OS processes open the same DB and run migrations: the Next server, `scripts/seed-port-da.ts`, and the cron scripts under `scripts/knowledge/cron/*`. A concurrent writer during a first-request migration throws SQLITE_BUSY immediately; since each `migration.up()` runs in its own `db.transaction()` (runner.ts:35-40), a BUSY mid-loop leaves some migrations applied and later ones pending — partial schema. — **Repro:** Confirmed no `busy_timeout` / `journal_mode=WAL` anywhere (grep over lib/ and scripts/ empty). (1) Fresh/restored `data/sessions.db` with migrations pending. (2) A scheduled timer/cron fires at its fixed slot (fx-rates 03:00, sanctions 04:00, market-refresh 05:00, market-indices 06:00 UTC) as a separate process; each `refresh-*.ts` calls `getStore()` → `new SessionStore()` → `runMigrations`. (3) Simultaneously another process (Next first request, manual `seed-port-da.ts`, or a knowledge/demo seed) also runs `runMigrations`. (4) Both compute the same pending list and enter `up()` write transactions; the first takes the reserved/exclusive lock, the second hits SQLITE_BUSY immediately and throws. (5) The throwing process aborts mid-loop with partial schema; a cron/seed process simply exits non-zero, leaving the schema partial until something else completes the loop. Raising `instances` above 1 makes the in-process race routine on every migration-bearing deploy. — **Fix:** Immediately after opening the DB in both `getDb()` and the `SessionStore` constructor, set `db.pragma('journal_mode = WAL'); db.pragma('busy_timeout = 5000');` before `runMigrations`. Optionally serialize concurrent openers with an advisory lock around the pending loop. Document `instances: 1` as load-bearing for migration safety.

### down() defined per migration but never invoked; no rollback CLI/path in production
- **File:** lib/migrations/runner.ts:34 — **Scenario:** The `Migration` interface forces every migration to implement `down()`, and most do (018/029 drop vec0/fts5 tables, 020 deletes seed rows, 023 drops the rewritten table), but `runMigrations()` only ever calls `migration.up(db)` (runner.ts:36). There is no `migrate:down` npm script, no `--rollback`/`--down` flag, and no code in `lib/`/`scripts/` that calls `migration.down()` or uses `getMigrationStatus()` for reversal. Once a destructive/buggy migration commits in prod, the only recovery is hand-written SQL or restoring the DB file; the `down()` bodies are dead code that falsely implies rollback is supported. — **Repro:** (1) A destructive migration ships (e.g. 022 `DROP TABLE market_benchmarks`, 023 `DROP TABLE ... CREATE ... INSERT seed`). (2) First `getStore()` after deploy runs `runMigrations`; runner.ts:34-41 executes only `up()` then records the version. (3) Operator finds the migration wrong; there is no command to run — grep `.down(` returns ONLY test files and one unrelated Playwright `page.mouse.down()`; no `migrate:down` in package.json; `getMigrationStatus` has no non-test callers. (4) Even an ad-hoc down-runner would not help for 022 (empty `down()`). — **Fix:** Either add an explicit rollback CLI (`scripts/migrate-down.ts` that runs `migration.down(db)` in a transaction and DELETEs the `schema_migrations` row) with a npm script and tests, or — if rollback is intentionally unsupported — delete the `down()` methods and the interface requirement and document "forward-only migrations; recover via DB restore."

### Each migration commits in its own transaction; no batch wrapping leaves partial-version state on crash
- **File:** lib/migrations/runner.ts:34 — **Scenario:** `runMigrations` wraps EACH pending migration in its own `db.transaction()` (runner.ts:35-40); there is no transaction spanning the whole batch. A hard kill (SIGKILL, OOM, container eviction) between migration N's commit and N+1's leaves the DB at an intermediate version — per-migration atomic but not batch-atomic. Combined with the no-rollback finding, the operator cannot cleanly revert to the pre-deploy version. No `journal_mode`/`synchronous` pragma is set (only `foreign_keys=ON`), so crash durability relies silently on SQLite defaults. — **Repro:** (1) Prod DB at v034; deploy of code expecting v040 starts. (2) deploy-vps.sh:32 → `seed-port-da.ts` → `runMigrations`; pending = [035..040], commits 035 durably (default DELETE journal + synchronous=FULL). (3) Process is SIGKILLed during 036; DB now has 001..036 applied, 037..040 pending. (4) No rollback possible (`down()` has zero non-test callers and impls are no-ops anyway). (5) `set -euo pipefail` aborts the script before `pm2 restart`, so the OLD app keeps serving against a 036 DB; next `getStore()` rolls forward only. (6) Nothing gates boot on a complete batch — `getMigrationStatus` has no callers and `/api/health` checks only `getSessionCount()`. — **Fix:** Make partial-batch state safe/observable: ensure code tolerates being one version off, or gate boot on `getMigrationStatus()` showing zero pending; document forward-only semantics; set explicit `journal_mode`/`synchronous` pragmas (or document the default reliance).

### Destructive up() drops/rewrites have no data-restoring down(), so even a manual rollback loses data
- **File:** lib/migrations/022-drop-market-benchmarks.ts:7 — **Scenario:** 022 `DROP TABLE IF EXISTS market_benchmarks` with a deliberately empty `down()`; 023/024 DROP+CREATE+reseed with `down()` that only DROPs (no row restore); 034 DELETEs duplicate `matches` rows before adding the unique index, with `down()` that only drops the index. Because `runMigrations` never calls `down()`, these are already irreversible in prod — and even if a rollback CLI were added, these `down()` bodies would not restore dropped/deleted data. Risk is irreversibility, not partial application (the DROPs are atomic within their per-migration transaction). — **Repro:** Track A (irreversibility, only if a rollback CLI is added): apply 022/023/024/034, then call e.g. `migration034.down(db)` — it drops the index but does not re-insert the permanently DELETEd duplicate `matches` rows. Track B (forward loss that fires unconditionally every fresh deploy): first `getStore()` → `runMigrations` runs the destructive `up()`s; 034 `DELETE FROM matches WHERE rowid NOT IN (...)` deletes duplicate live match rows; 023/024 DROP+reseed discard runtime-fetched bunker/eua rows. The deploy path has NO DB backup before this runs. — **Fix:** Document data-destroying migrations as irreversible and require an out-of-band backup of the affected table (or capture pre-state into a backup table in `up()`). If a rollback CLI is added, flag empty/index-only `down()` bodies as lossy so operators are not misled.

### Migration 023 unconditionally DROPs bunker_prices then recreates+reseeds (loses runtime price rows on re-run)
- **File:** lib/migrations/023-bunker-prices-rewrite.ts:14 (DROP at :16) — **Scenario:** `up()` runs `DROP TABLE IF EXISTS bunker_prices;` then bare `CREATE TABLE` + 10 static seed rows. `bunker_prices` is a live cache written at runtime by `lib/market/bunker-repository.ts:27` (cron `scripts/knowledge/cron/refresh-bunker.ts`, sources usda/shipandbunker, one new row per calendar date). MED (not CRITICAL) because the data is cron-reconstructable. — **Repro:** PATH A: on a populated prod DB `DELETE FROM schema_migrations WHERE version=23;` then restart → next `runMigrations` re-queues 23 → `up()` DROPs all accumulated rows → reseeds 10 static rows. PATH B (most plausible, no deliberate edit): restore a DB snapshot taken before v23 was applied but whose `bunker_prices` already holds fetched rows → next boot treats v23 as pending → same wipe. ## Top 5 Risks
1. **HIGH — deploy-vps.sh eager migrate targets the wrong database in demo mode:** the documented primary deploy migrates a throwaway `data/sessions.db` while the demo server serves `data/demo-seed.db`, so the served DB ships one migration behind every deploy and relies entirely on the fragile lazy path.
2. **MED — Pending migration can stay unapplied while traffic is served; root-layout getStore() construction is wrapped in catch{}:** a failing migration during the first `getStore()` is silently swallowed, presenting a stale schema as degraded-but-200 UI indefinitely instead of a loud failure.
3. **MED — USE_MIGRATION_RUNNER=false creates only 4 tables but ~60 call sites query the rest:** a single mis-set flag (un-enforced outside prod and bypassed by the CI deploy path) boots a half-broken DB where dashboard/market/AI-audit/sanctions/Pipedrive break.
4. **MED — Lazy concurrent runMigrations have no WAL and no busy_timeout:** concurrent cron/seed/server processes opening the same DB during a pending-migration window hit immediate SQLITE_BUSY, leaving a partial schema.
5. **MED — down() is never invoked and no rollback path exists (compounded by no batch transaction):** once a destructive or buggy migration commits in prod, the only recovery is hand-written SQL or a DB-file restore, and a crash mid-batch leaves an unrevertable intermediate version.

## Considered & Dismissed
- **No eager migration at boot (instrumentation.register):** refuted — `deploy-vps.sh:32` runs `seed-port-da.ts` (`runMigrations`) before `pm2 restart`, and `/api/health` + any first request self-heal via lazy apply; the runner is idempotent. (Note: the demo-DB-path mismatch is captured separately as the HIGH finding.)
- **deploy-vps.sh skips preflight → USE_MIGRATION_RUNNER guard never enforced:** structural observation true, but `seed-port-da.ts` applies all 40 migrations to `data/sessions.db` before restart, so the 4-table else branch is harmless on that path; also the cited `scripts/session-store.ts:47` path is wrong (it is `lib/session-store.ts:47`).
- **vec0/fts5 CREATE VIRTUAL TABLE shadow-table re-run loop (018/029):** refuted — wrapped in `db.transaction()` (no implicit commit for vec0/fts5 in better-sqlite3@12.10.0) and `IF NOT EXISTS`, so re-run is a clean no-op; self-filed as LOW asserting the loop does NOT occur.
- **Migrations 001-005 idempotency:** confirmed safe — only `CREATE ... IF NOT EXISTS`, no seeds, no out-of-band destructive ops; no failure path exists.
- **Migration 008 ALTER idempotency:** the raw ALTER is unreachable on re-run (PRAGMA `table_info` column guard + table guard + version gate + no out-of-band call site). (The separate silent-skip aspect of 008 is a confirmed MED finding above.)
- **Migration 018/029 orphaned shadow tables on rollback:** refuted — shadow tables enroll in the same write transaction and unwind atomically; all statements use `IF NOT EXISTS`; both self-filed as defensive non-bugs.
- **Migration 020 INSERT OR IGNORE keeps stale values:** refuted — 020 is the first writer for its key and the alternate writer writes byte-identical values; stylistic only.
- **023/024 bare CREATE TABLE lacks IF NOT EXISTS:** refuted — the leading `DROP TABLE IF EXISTS` in the same `db.exec` batch guarantees the table is absent before CREATE; self-recovers on replay.
- **023/024 seed INSERT lacks OR IGNORE / ON CONFLICT:** refuted — the preceding DROP makes the table empty at seed time; runner version-gate prevents re-run; idempotency tests assert COUNT==1.
- **migration033 7x unguarded ALTER ADD COLUMN:** refuted as a live defect — version-gated and transactional in the runner; latent code smell only (captured indirectly via the 035 fix recommendation).
- **migration036 ALTER ADD COLUMN:** refuted — guarded by a `PRAGMA table_info(matches)` existence check with a dedicated double-`up()` regression test already present.

## Verdict: is a clean deploy guaranteed to reach the correct schema?

**no**

A clean deploy is NOT guaranteed to land the correct schema on the served database. There is no eager migrate at server boot (`instrumentation.register()` never calls `getStore()`), so migrations apply lazily on the first `getStore()` — and on demo deploys the only eager step (`deploy-vps.sh:32`) migrates a throwaway `data/sessions.db` while the runtime serves `data/demo-seed.db`, which ships one migration behind on every deploy and is brought current only by the lazy path. That lazy path is fragile: in `app/layout.tsx` the migration-bearing `new SessionStore()` runs inside best-effort `catch{}` blocks that swallow a failing migration into a silently-degraded 200 response, and `USE_MIGRATION_RUNNER=false` (un-enforced outside prod, bypassed by the CI deploy path) substitutes a 4-table subset. The runner itself is idempotent and per-migration atomic and pm2 `instances:1` reduces in-process races, so a healthy first request usually does converge — but "usually converges via a lazy, error-swallowing, wrong-DB-targeted path" is not a guarantee.
