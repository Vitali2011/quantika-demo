# Parser Readiness Audit — "If we connect a real client Gmail tomorrow"

> **Date:** 2026-06-22
> **Question (founder):** Как отработают наши парсеры, если **сейчас реально подключить живую почту клиента** к приложению (а не демо-корпус)?
> **Method:** 3 read-only recon агента (Sonnet:high, dev-VPS) → ingestion-tract / parser-inventory+evals / failure-modes. Static analysis + corpus inspection. **No parsers were run against a live LLM** (would need API budget). Source recons: `docs/research/recon-parser-{ingest,evals,failmodes}-2026-06-22.md`.

---

## TL;DR — вердикт

**НЕ готово к боевому клиентскому ящику сегодня.** Два независимых блока проблем:

1. **Тракт приёма** работает для разового демо-подключения, но **связь умирает через ~1 час** (нет refresh-токена) и видит только **50 последних писем, только текст** (вложения/PDF игнорируются).
2. **Парсеры зелёные на unit-тестах, но это мокнутый LLM — реальной точности мы НЕ знаем.** Прогонов с живым LLM (progonq) для 4 из 7 парсеров нет. А реальные брокерские письма устроены ровно так, как парсеры **молча ломаются**: флотские циркуляры (много судов), рыночные циркуляры (много грузов), форварды, recap во вложении, не-английский.

**Самое опасное — не падения, а тихие потери.** Парсер не кидает ошибку — он возвращает первое судно из восьми, роняет 7 грузов из циркуляра, ставит null вместо recap. Брокер увидит доску, которая **выглядит нормально, но неполна/неверна**.

**Дешёвый первый шаг до любых фиксов:** прогнать живой progonq (367 готовых сценариев, ~$10–50 API) → заменить догадки реальными цифрами точности. Сейчас летим вслепую.

## 1. Тракт приёма (recon A)

**Что УЖЕ проведено** (`lib/google.ts`, `app/api/auth/google`, `app/api/emails/fetch`, `app/api/ai/*`):

- Полный OAuth-callback → сессия → `accountId` (email) как ключ.
- Pull-fetch 50 последних писем (только text/plain + html-strip).
- Персист сырых писем + parsed_results в SQLite (кросс-сессионный кэш, mig 031).
- Полный конвейер classify→parse-cargo→parse-vessel→parse-recap→match.
- Inline-парс через `POST /api/parser/email` (auth + rate-limit, без персиста).

**Блокеры для живого ящика** (file:line в recon A):

| #      | Блокер                 | Тяжесть     | Суть                                                                                                                                                                                             |
| ------ | ---------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **G1** | Нет refresh-токена     | 🔴 CRITICAL | `access_type:'online'` (`lib/google.ts:19`) → токен живёт ~1ч, потом Gmail 401 на каждый fetch → клиент должен пере-логиниться. Фикс: `offline` + `prompt:consent` + хранить refresh_token в БД. |
| **G2** | Нет re-polling         | 🟠 HIGH     | Письма тянутся **один раз** на `/processing`. Новые письма после логина невидимы. Минимум — кнопка «обновить ящик»; правильно — Gmail Pub/Sub watch.                                             |
| **G3** | Потолок 50 писем       | 🟠 HIGH     | `EMAIL_FETCH_COUNT=50` (`lib/constants.ts:66`). Активный брокер легко имеет >50 запросов → хвост обрезан. Фикс: пагинация по `pageToken`.                                                        |
| **G4** | Нет вложений/OCR       | 🟡 MED      | `extractBody()` берёт только текст. Cargo-оффер/recap в PDF/docx → **пустое тело** → ноль распознанных полей.                                                                                    |
| **G7** | Токен не durable       | 🟡 MED      | Токен живёт в in-memory сессии. Рестарт сервера → все клиенты пере-логинятся; фоновые операции (Pub/Sub, cron) токен достать не могут. Нужна таблица `oauth_tokens` по `accountId`.              |
| G5     | Нет inbox-фильтра      | 🟡 MED      | `q:''` тянет вообще всё (рассылки, системные) → жжёт токены из лимита 50.                                                                                                                        |
| G6     | Нет группировки тредов | ⚪ LOW      | Плоский `messages.list`, не `threads.list` → контр-офферы плодят дубли.                                                                                                                          |

**Минимально-жизнеспособное подключение реального ящика = G1 + G2(кнопка) + G3.** Production-grade = G1–G7.

## 2. Готовность парсеров (recon B) — зелёно, но вслепую

**⚠️ Ключевой нюанс: «100% pass» = unit-тесты с ЗАМОКАННЫМ LLM, НЕ реальная точность.** Прогонов с живым LLM (progonq) для classify / parse-cargo / parse-vessel / parse-recap **нет** — последние progonq-репорты есть только у `match` (R6) и `draft-quote` (R3). 367 corpus-сценариев лежат готовые, но непрогнанные. Цифры роадмапа («classify 70.8% / parse-recap 45-58%») — старые progonq, сейчас не воспроизведены.

**Известный открытый баг (match R6):** судовое ограничение свободным текстом `"no Ukraine voyage"` не парсится pre-фильтром → пара Odesa проходит со score 25.9 weak вместо hard-блока (`etms-match-013`).

## 3. Тихие провалы на реальной почте (recon C) — самый ценный блок

Прогон по структуре 153 демо-писем + 165-сценарного classify-corpus. **20 режимов провала; почти все SILENT** (возвращают пусто/неверно без ошибки). Топ по тяжести на реальном ящике:

| Ранг | Режим                                    | Парсер             | Что теряется                                                                                     | Частота на реальном ящике           |
| ---- | ---------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------ | ----------------------------------- |
| 1    | **FM-06 флотский циркуляр**              | parse-vessel       | Письмо с 8 судами → извлекается **только первое**, 7 невидимы движку                             | 🔴 HIGH (циркуляры — норма)         |
| 2    | **FM-14 рыночный циркуляр**              | parse-cargo        | 8 грузов через `++++` → если LLM не отдал `items:[]`, остаётся 1, **7 молча падают**             | 🔴 HIGH                             |
| 3    | FM-03 обрезка 3000 симв.                 | classify           | `MAX_EMAIL_BODY_CHARS=3000`, 16/153 письма длиннее → хвост с деталями режется → мисклассификация | 🟠 MED-HIGH                         |
| 4    | FM-08 битый JSON → all-null              | parse-recap        | `callAiText` глотает `JSON.parse`-ошибку → recap со всеми null принимается как успех             | 🟡 MED                              |
| 5    | FM-12 FD = Free vs Full Despatch         | parse-recap        | «PDPR/FD ALL ENDS» → ставит ставку демереджа в despatch вместо null                              | 🔴 HIGH (FD — стандарт в сухогрузе) |
| 6    | FM-09 recap под внешней подписью         | parse-recap        | Внешний слой = подпись форварда, recap внутри → анти-галлюцинация срабатывает рано → null        | 🟡 MED (Outlook-форварды)           |
| 7    | FM-13 «Charterers» как имя               | parse-recap        | Роль-существительное из клаузы попадает в поле имени стороны                                     | 🔴 HIGH (в каждом CP)               |
| 8    | FM-10 евро-десятичная «3.858 TON»        | parse-recap/vessel | 3.858 = 3858 MT прочитано как 3.858                                                              | 🟡 MED (Южная/Восточная Европа)     |
| 9    | FM-16 полностью арабский/греческий текст | parse-cargo/vessel | Без латинской транслитерации → OTHER → невидимо движку                                           | 🟡 MED (Med-трейды)                 |
| 10   | FM-19 days_without_reply=2000+           | classify           | Старые треды дают абсурдные дни без ответа (нет верхнего cap)                                    | ⚪ LOW (косметика)                  |

**Деление по двум слабейшим парсерам:**

- **classify ~70%** — наполовину **артефакт стале-GT**: 18/165 сценариев имеют `urgency=low` там, где промпт уже запрещает low (GT сделан до R3/R4-правил; модель права, бенч устарел). Прогнать `normalizeUrgency()` по corpus-файлам → точность подскочит ~70%→>90% без правок модели. НО эти 18 стале-записей **маскируют реальные ошибки** — настоящий процент неизвестен.
- **parse-recap ~45–58%** — корпус **12 сценариев (3 реальных)** = статистически бесполезно. Тяжёлые поля: owners/charterers/account (роль вместо имени), despatch (FD-путаница), vessel_dwt (евро-десятичная), laycan (ETA вместо LAYCAN). Нужно **50+ реальных recap'ов** разных форм (GENCON/NYPE, geared/gearless, EUR/USD, multi-port).

## 4. Вердикт + приоритеты

**На вопрос «подключим завтра — как отработают»:** простые письма (один груз / одно судно / чистый текст) — хорошо. Но реальный брокерский ящик доминируют ровно те паттерны, что ломаются **тихо**: флотские/рыночные циркуляры, форварды, вложения, не-английский. Брокер получит правдоподобную, но неполную доску.

**Очередь (recon→план→exec по конвейеру, когда дашь go):**

| Приор  | Работа                                                                                      | Почему                                                                                                               |
| ------ | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **P0** | **Живой progonq-прогон** 367 сценариев (~$10–50)                                            | Заменить «зелёные моки» реальными цифрами. Диагностика ДО фиксов — иначе чиним вслепую.                              |
| **P0** | **Multi-item hardening** (FM-06 + FM-14)                                                    | Гарантировать, что `items:[]` всегда используется; флот/рынок-циркуляры — самая частая и самая дорогая тихая потеря. |
| **P0** | **Ingestion G1 (refresh-токен)**                                                            | Без него любое живое подключение умирает за час.                                                                     |
| **P1** | Ingestion G2 (кнопка refresh) + G3 (пагинация >50)                                          | Новые письма + полный ящик.                                                                                          |
| **P1** | parse-recap: расширить corpus до 50+ реальных recap'ов + FD-дизамбигуация + outer-signature | Самый слабый парсер; нужны данные клиента.                                                                           |
| **P1** | Ingestion G4 (вложения/OCR)                                                                 | PDF/docx-офферы иначе = пустой парс.                                                                                 |
| **P2** | classify: обновить 18 стале-GT (`normalizeUrgency` по corpus) + cap days_without_reply      | Дешёвый подъём метрики + честность бенча.                                                                            |
| **P2** | match R6: structured `restrictions` (no-Ukraine и т.п.)                                     | Закрыть известный open fail.                                                                                         |

**Зависимость от данных клиента:** P1 parse-recap и калибровка classify/parse-recap до 95%+ требуют **реальных писем от партнёра** (recap'ы + размеченные по срочности) — это та самая блокировка из роадмапа («classify/parse-recap ждут данных партнёра»). Подключение живого ящика её естественно снимает.
