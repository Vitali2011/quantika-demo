## Контекст и проблема

После Phase 1.5 осталось 14 провальных сценариев. Анализ исходных писем показал,
что «провалы» — это **четыре разных типа проблем**, и только один из них про промт:

| Слой                    | Сценарии                                | Тип фикса          |
| ----------------------- | --------------------------------------- | ------------------ |
| Eval-скрипт нечестный   | 059 (+ скрытая обрезка многогрузовых)   | 1 строка конфига   |
| Scorer слишком строгий  | 071, 073, 037, 048                      | нормализация строк |
| Корпус врёт             | 062, 086 (CBM/ft³), + находки ре-аудита | правка эталонов    |
| Модель реально ошиблась | 021, 078, 016, 037 (POC/EC)             | промт few-shots    |

### Ключевая находка №1 — CBM/ft³ это ошибка КОРПУСА, не модели

Сценарии 062 и 086: корпус-эталон размечен `CBM/MT`, модель отвечает `ft³/MT`.
**Модель права.** Stowage factor риса физически — 1.2–1.8 м³/т = 42–63 ft³/т.
Цифры «48-50» и «62» — это кубические футы (в 086 письмо прямо пишет `62'` с
апострофом-футом). Промт (строки 170–171) уже корректно учит модель: `47-49'` → `ft³/MT`.
Разметчик корпуса ошибся. Чинить надо корпус, не промт.

### Ключевая находка №2 — 059 это баг eval-скрипта

`run-parse-cargo.ts:321` задаёт `maxTokens: 4096`. Продакшн-роут через `callAiJson`
использует `max_tokens: 16000` (`ai-provider.ts:73`). Письмо 059 = 11 грузов; 11
JSON-объектов с обёртками `{value, confidence, source_text}` не влезают в 4096
токенов. Модель упирается в потолок → JSON обрывается → `{items: []}`. В продакшене
059 распарсился бы нормально. Eval искусственно калечит модель на многогрузовых письмах.

### Ключевая находка №3 — нет честного сравнения Flash vs Pro

Wave-γ bakeoff выбрал `gemini-2.5-flash` победителем для parse-cargo (Pro: 70.8%
pass, 25% ModelErr, ×3 цена, ×2 латентность). Но весь progonq-эвал R13–R19 гонялся
на `gemini-2.5-pro`. Когда/почему вернулись на Pro — в истории не зафиксировано.
Подозрение: 25% ModelErr у Pro в bakeoff — та же болезнь, что в 059 (обрезка по
токенам), т.е. Pro проиграл нечестно. Нужен контролируемый замер на честной линейке.

## Подход: два чекпоинта

```
Чекпоинт 1: ЧЕСТНОСТЬ ИЗМЕРЕНИЯ (модель/промт не меняются)
  ├─ 1a. Eval-скрипт: maxTokens 4096 → 16000
  ├─ 1b. Scorer: нормализация строк (регистр/диакритика/пробелы/пунктуация)
  ├─ 1c. Корпус: полный ре-аудит всех 95 сценариев
  ├─ 1d. R20a ×2 — на gemini-2.5-pro И на gemini-2.5-flash (один честный корпус)
  └─ ГЕЙТ: R20a(pro) ≥ R19 (81 string). Если ниже — ре-аудит внёс ошибку, разбор.

Чекпоинт 2: УЛУЧШЕНИЕ МОДЕЛИ (только промт)
  ├─ 2a. Few-shots: EC/WC/NC/SC побережья, POC=Чорноморськ
  ├─ 2b. Правило сегментации карго-лотов (021/078)
  ├─ 2c. Фикс пере-краткости Rule 11 (016)
  └─ R20b на модели-победителе из 1d
       ГЕЙТ: R20b > R20a, ноль регрессий на ранее зелёных.
```

**Принцип честной атрибуции:** R20a = «насколько модель хороша на самом деле»
(линейку починили — модель та же). R20b = «что дал промт». Две разные цифры.

## Чекпоинт 1 — детали

### 1a. Eval-скрипт — maxTokens

`scripts/progonq/run-parse-cargo.ts:321`: `maxTokens: 4096` → `16000`.
Приводит eval в соответствие с продом. Риск нулевой — устранение бага.

### 1b. Scorer — нормализация строк

В функции сравнения портов/карго — нормализация **перед** строковым равенством:

- регистр → lowercase
- диакритика → ASCII-фолд (`Bandırma` = `Bandirma`, `Constanța` = `Constanta`)
- пробелы/пунктуация → схлопывание

**Граница (сознательно):** НЕ делаем fuzzy/Levenshtein. Реальные опечатки модели
(`Aleaxandroupolis`, `Duala`) должны оставаться красными — иначе спрячем настоящие
ошибки, а цель противоположная.

### 1c. Корпус — полный ре-аудит всех 95

Метод (паттерн progonq — независимый cold-session ревьюер):

- 5 субагентов параллельно, батч ~19 сценариев. Каждый = доменный эксперт по
  морскому чартерингу. Читает `input.body` + `reference_output`, проверяет:
  единицы (CBM vs ft³ по физике!), порты, веса, число items, формат ConfidenceField.
- Субагент возвращает список подозрений: `scenario-XXX, поле, эталон=A, должно=B, причина`.
- **Субагент НЕ видит вывод модели** — судит эталон только по письму и доменной
  логике. Исключает подгонку эталона под модель.
- Сверочный проход (главная сессия): свожу находки, спорные — перечитываю письмо.
  Применяю только уверенные правки. Все правки фиксируются в журнале (ниже) с обоснованием.

Известный улов на старте: 062, 086 (CBM→ft³). Ожидается ещё 3–6 однотипных.

### 1d. Контролируемый замер Flash vs Pro

После 1a–1c (честная линейка готова) — прогнать R20a **дважды**:

- `PARSE_CARGO_GEMINI_MODEL=gemini-2.5-pro` @ us-central1
- `PARSE_CARGO_GEMINI_MODEL=gemini-2.5-flash` @ us-central1

Один и тот же честный корпус, один scorer. Закрывает дыру «Flash vs Pro на полных
95 сценариях», которой нет в истории проекта. Дёшево (один лишний прогон ~20 мин).

## Чекпоинт 2 — детали (только `lib/prompts/parse-cargo.ts`)

Все правки — обобщаемые принципы, не «запомни ответ для сценария X».

### 2a. Морские сокращения портов

В RULE 4 (там уже `Nemrut → Nemrut Bay`):

- `EC/WC/NC/SC + [страна]` → `East/West/North/South Coast [страна]`
- `POC` в контексте Чёрного моря → `Port of Chornomorsk` (confidence uncertain)

Граница overfit: правило для _класса_ сокращений, не список «строка→ответ».

### 2b. Сегментация карго-лотов (021, 078)

Каждый блок «цена + маршрут + груз» = отдельный item. Разделители (`+++`, пустые
строки, «And», нумерация) — границы лотов. Один маршрут + один груз = один item,
даже если описан многословно.

### 2c. Фикс пере-краткости Rule 11 (016)

Краткость ≠ потеря фактов. Существенные детали груза (тип, упаковка, требования к
судну) сохраняются; убирается только водянистость («The cargo consists of…»).

### Сознательно НЕ чиним промтом

Опечатки модели (089 `Aleaxandroupolis`, 082 `Duala`) — предел Gemini 2.5 Pro на
данном промте. Накрутка промта под опечатки = подгонка. Если останутся красными —
это честный потолок, вход в Phase 3 (Bedrock Opus как парсер).

## Финал Phase 1.6 — Чекпоинт 2 не подтвердился, найден баг eval-скрипта

### Задача 8 — R20b показал «регрессию», systematic-debugging вскрыл баг измерения

Прогон R20b (новый промт) дал 78/85 против R20a-pro 82/86 — выглядело как −4 string. Вместо слепого отката — систематическая отладка.

**Корневая причина (доказана сырым выводом модели):** Gemini возвращает результат в трёх формах JSON: `{items:[...]}`, `[{items:[...]}]` и `[{item},{item},...]` (голый массив). Eval-скрипт (`runScenario`) обрабатывал только первые две. На третьей форме брал `raw[0]` (первый item), не находил `.items` и записывал `{items:[]}` — молча выбрасывал все грузы. Для 4 многогрузовых сценариев (016/027/059/064) eval показал 0 грузов, хотя модель честно вернула все. Это баг Задачи 1 (YAGNI-решение «только две формы»).

**Фикс:** `extractItems` обрабатывает все три формы. TDD, 19/19 тестов, smoke подтвердил 059 → 11 грузов. Коммит `13f862a`.

### Re-run обоих промтов на починенном eval-скрипте

| Прогон | Промт              | Eval-скрипт | String    | Semantic  |
| ------ | ------------------ | ----------- | --------- | --------- |
| R20a2  | старый (cda3019)   | починенный  | **82/95** | **87/95** |
| R20b2  | новый (Чекпоинт 2) | починенный  | 79/95     | 86/95     |

**Вердикт: правки промта Чекпоинта 2 — net −3 string / −1 semantic.** Гипотеза «есть реальные ошибки модели, чинятся промтом» честным eval **опровергнута**. По сценариям: RULE 11 физически не влияет на ports-only string-счёт; EC/WC дала спилловер-регрессию (067: Med→Mediterranean); RULE 10 смешанная (помогла 016/037/052, навредила 039).

### Решение: Phase 1.6 шипит только Чекпоинт 1

3 коммита правок промта откатаны (`254c472` — возврат `parse-cargo.ts` к состоянию cda3019).

**Что шипим:** честный eval-скрипт (maxTokens + array-unwrap + extractItems) + нормализация scorer (базовые буквы) + ре-аудит корпуса (18 файлов, 16 ошибок CBM/ft³ + 2 опечатки).

**Итог Phase 1.6:** честные **82 string / 87 semantic** на линейке, которой теперь можно доверять (vs R19 81/85 на старой сломанной линейке). Чекпоинт 2 — отрицательный результат, тоже ценный: теперь _знаем_, что эти правки промта не работают.

**Замечание для Phase 3:** semantic-судья почти не штрафовал за путаницу CBM/ft³ — слепое пятно судьи. Реальный потолок Gemini 2.5 Pro на честной линейке — 82/87; дальнейший рост — это смена модели (Bedrock Opus) либо точечная работа с оставшимися ~13 провалами.
