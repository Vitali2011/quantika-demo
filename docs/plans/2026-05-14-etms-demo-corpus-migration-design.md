# Дизайн: полная миграция демо-корпуса на ETMS (154 письма)

**Дата:** 2026-05-14
**Статус:** одобрен, готов к `writing-plans`
**Ветка:** `feat/etms-demo-corpus-migration`

## Контекст

Демо-режим quantika-demo показывает заранее заготовленные письма
(`lib/sample-data/*.json`) и их распарсенный вывод. Две недели назад
коммит `a321e82` попытался заменить 12 curated-писем «V2» на 154 реальных
письма ETMS-корпуса, но сделал это наполовину: заменил email-файлы (новые
hex-ID), но НЕ распарсенный вывод и НЕ тесты (там остались старые `sample-NN`
ID). Рассинхрон сломал 23 теста, и миграцию откатили в PR #141 — сейчас `main`
снова на консистентном зелёном V2-наборе из 12 писем.

Эта инициатива делает миграцию правильно и целиком: письма + классификация +
парсинг + тесты — всё согласованно в одном такте.

Дизайн-док `docs/plans/2026-05-14-email-persistence-design.md` упоминал эту
миграцию как отложенную вне-scope работу. Email-persistence layer (Wave δ,
таблицы `emails`/`parsed_results`) — ортогонален: и демо, и реальный корпус
остаются эфемерными в session JSON.

## Решения (зафиксированы при ревью)

| Вопрос                             | Решение                                                                                                                                                                                                                                |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Приватность: корпус реальных писем | **Коммитить как есть.** Это брокерские циркуляры (массовые рыночные рассылки), не личная переписка. Source `.private/etms-corpus.json` остаётся в gitignore, в git идут только производные `lib/sample-data/` файлы.                   |
| Свежесть дат                       | **Сдвигать только envelope-дату.** Генератор вычисляет `_meta.emailDateOffsetDays`; тела писем не трогаем (иначе ломается `source-text-validity`), laycan'ы в телах остаются замороженными — принятый частичный рассинхрон шапка↔тело. |
| Реестр судов                       | **Принять меньше записей.** Парсер `/api/vessel/[imo]` не трогаем. ~7 писем с `IMO:`-блоками в новом корпусе → реестр меньше. Тесты переписываем под реальное судно из нового корпуса.                                                 |
| Пайплайн генерации                 | **Офлайн-скрипт.** Новый `scripts/build-sample-data.ts` вызывает те же lib-функции, что и endpoints. Воспроизводимо, не нужен живой сервер.                                                                                            |

## Архитектура: единый офлайн-генератор

Новый скрипт `scripts/build-sample-data.ts` — single source of truth для
демо-фикстур. Запуск вручную (`npm run build:sample-data`), читает
`.private/etms-corpus.json`, вызывает lib-функции `classify` / `parse-cargo` /
`parse-vessel` / `parse-recap` (те же, что используют API-маршруты), и
атомарно перезаписывает 8 файлов в `lib/sample-data/`. Принцип: фикстуры
никогда не правятся руками — только перегенерируются скриптом.

## Поток данных (что делает генератор)

1. **Загрузка** — 154 письма из `.private/etms-corpus.json` (source остаётся
   в gitignore).
2. **Классификация** — каждое письмо через `classify` → одна из категорий.
   Разбивка по 4 файлам: `cargo-inquiries.json` / `vessel-positions.json` /
   `fixture-recaps.json` / `client-replies.json`. Точные числа берём из факта
   классификации (ориентир из `a321e82`: ~97 / ~53 / ~3 / ~1), **не хардкодим**.
3. **Date `_meta`** — для каждого письма вычисляем `emailDateOffsetDays` =
   (дата письма − дата самого свежего письма в корпусе). Самое свежее = офсет 0.
   `rebaseDates()` при сидинге сдвинет шапки так, что демо всегда выглядит
   свежим. Тела писем не трогаем.
4. **Парсинг** — cargo-письма через `parse-cargo`, vessel — через
   `parse-vessel`, recap — через `parse-recap`. Реальный Gemini: ~154 вызова
   классификации + ~150 вызовов парсинга. Бюджет: Gemini Flash, ориентировочно
   $1–4. `sourceText` в выводе — дословные подстроки реальных тел писем.
5. **Запись** — `demo-parsed-cargoes.json`, `demo-parsed-vessels.json`,
   `demo-classifications.json` + 4 email-файла. Сохраняем 2 синтетических
   fixture-записи `demo-cargo-economics` / `demo-vessel-economics` (они не из
   корпуса, нужны для EconomicsTab-тестов).
6. **Коммит** — все 8 производных файлов идут в git.

## Обработка дат в распарсенном выводе

Сейчас `demo-parsed-cargoes.json` хранит laycan как относительный офсет
(`"+12d"`), а `resolveDemoParsedCargoes(now)` превращает в абсолютную дату.
Поскольку тела писем заморожены, реальный парсинг даёт абсолютные laycan'ы.
Решение: распарсенные фикстуры хранят абсолютные значения как есть;
`resolveDemoParsedCargoes` / `resolveDemoParsedVessels` упрощаются до passthrough
(relative-резолв остаётся только для 2 синтетических economics-записей, если им
нужен). `rebase.ts` остаётся для envelope-дат email-файлов.

## Реестр судов

Парсер `/api/vessel/[imo]` не трогаем. В ETMS-корпусе ~7 писем с явными
`IMO:`-блоками — реестр просто меньше. `route.test.ts` переписываем: вместо
«CARBON LADY / 9456783» пиним реальное судно, найденное в новом корпусе
(конкретный IMO+имя фиксируем на этапе реализации, увидев распарсенный вывод).

## Реализация

Файлов в работе ~12–16: 1 генератор-скрипт + 8 data-файлов + 6 тестов +
правки `demo-parsed-cargoes.ts` / `rebase.ts` / `types.ts` + `package.json`.
Проект с историей recurring-чейнов (Q1-chain pattern), прошлая попытка сломала
23 теста → используем **`task-okestor-deep`** (strict-mode: systematic-debugging
в BLOCK_AND_FIX loop, 9-class boundary QA, PI3-enforcement), а не
`dev-pipeline-deep`.

## Риски

- **LLM-парсинг недетерминирован** — повторный запуск генератора даёт слегка
  другой вывод. Митигация: генератор запускается один раз, вывод коммитится и
  дальше неизменен; тесты валидируют структуру, а не точные значения.
- **Классификация может ошибиться** на messy forwarded-цепочках — письмо
  попадёт не в ту категорию. Митигация: после генерации — глазами просмотреть
  распределение по категориям на адекватность.
- **`parse-recap` всего на ~3 письмах** — мало покрытия, но это отражает
  реальный корпус.

## Вне scope

- Email-persistence layer (Wave δ) — отдельная инициатива.
- Изменение парсеров `parse-cargo` / `parse-vessel` / `parse-recap` /
  `/api/vessel/[imo]` — генератор использует их как есть.
- Обновление корпуса в `.private/` (импорт новых писем из Gmail).
