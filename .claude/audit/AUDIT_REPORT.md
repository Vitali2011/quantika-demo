# Аудит quantika-demo (2026-04-15)

## Краткая сводка

Quantika-demo — Next.js 14 продукт для AI-триажа freight email
(подключение к Gmail → классификация → парсинг cargo/vessel/recap →
матчинг → расчёт комиссий). Стек современный, без явных архитектурных
ужасов, OAuth настроен корректно, явных «дыр в безопасности с утечкой
секретов» нет. Главные проблемы — **операционные и эксплуатационные**,
а не архитектурные: продукт работает, но в текущем виде не готов к
production-нагрузке и к командной разработке.

Три самых болезненных места: (1) **сессии живут только в памяти** —
любой рестарт сервера обнуляет всю работу пользователя; (2) **нет CI и
тестов** (1 файл с 8 тестами на 5 600 строк кода) — любое изменение
рискованно, ревью невозможно автоматизировать; (3) **скрытые
TypeScript-ошибки** (`ignoreBuildErrors: true`) и **5 уязвимостей в
зависимостях** уровня HIGH — баги проезжают на прод без сопротивления.
Плюс есть очевидные пробелы в наблюдаемости (нет логирования, нет
health-чека, нет трекинга ошибок) — узнаешь о падении только когда
пользователь напишет.

Хорошее: код функциональный, OAuth с правильными httpOnly+sameSite
куками, нет `dangerouslySetInnerHTML`, нет хардкода секретов в
исходниках, классификация и парсинг через AI работают, доменные модели
в `lib/types.ts` хорошо описаны. Это не «спасать горящий дом» — это
«покрасить и подкрепить фундамент перед заездом жильцов».

### 1. Качество кода и архитектура (8 находок: P0=0, P1=4, P2=3, P3=1)

#### finding-001 [P1]: Бизнес-логика смешана с UI на dashboard

ЧТО НАШЁЛ: `app/dashboard/page.tsx` — один файл на 571 строку, делает
загрузку сессии, фильтрацию писем, группировку по статусам, проверку
freshness и рендер всего UI.
ПОЧЕМУ ВАЖНО: невозможно протестировать логику отдельно от UI;
рефакторинг ломает оба слоя сразу; новые фичи на dashboard будут
накапливать сложность экспоненциально.
СЕЙЧАС: 571 LOC в одном компоненте, 0 тестов на эту логику.
ПОТОМ: вынести группировку/фильтрацию в `lib/dashboard-queries.ts`,
покрыть тестами, страница ≤200 LOC.
СЛОЖНОСТЬ: M (4-6 часов).
РИСК ЕСЛИ НЕ ДЕЛАТЬ: через 2-3 месяца этот файл станет 800-1000 LOC и
«трогать его страшно».
Файлы: `app/dashboard/page.tsx:23-131`

#### finding-002 [P1]: Дублирование UI-хелперов в 4 detail-страницах

ЧТО НАШЁЛ: функции `safeRender`, `getConf` и компонент `ConfIcon`
скопированы один-в-один в 4 файла: fixture, match, cargo, vessel.
ПОЧЕМУ ВАЖНО: правка в одном месте не подхватится в трёх других;
вероятность расхождения логики со временем — 100%.
СЕЙЧАС: 4 копии × ~30 LOC = 120 LOC дублирования.
ПОТОМ: один `lib/ui-render.ts`, импорт в 4 страницах.
СЛОЖНОСТЬ: S (30-60 минут).
РИСК ЕСЛИ НЕ ДЕЛАТЬ: следующая правка отображения confidence будет
сделана в одной странице, две другие покажут старое — «баг, который не
повторяется».
Файлы: `app/{fixture,match,cargo,vessel}/[id]/page.tsx` (строки 12-20
в каждом)

#### finding-003 [P1]: Дублирование парсинг-утилит в 3 AI-роутах

`app/api/ai/parse-recap/route.ts:12,13`,

### 4. Безопасность (5 находок: P0=2, P1=2, P2=1, P3=0)

#### finding-017 [P0]: Сессии только в памяти, теряются при рестарте

ЧТО НАШЁЛ: `lib/session.ts:25` — `Map<sessionId, SessionData>` в
памяти процесса, TTL 1 час, `sessionStore` обнуляется на рестарт PM2.
ПОЧЕМУ ВАЖНО: пользователь подключил Gmail, прогнал 5 минут AI-
обработки 100 писем, в этот момент PM2 рестартанул процесс — вся
работа потеряна. Восстановления нет.
СЕЙЧАС: 100% потеря данных при любом рестарте.
ПОТОМ: SQLite на диске или Redis — переживает рестарт.
СЛОЖНОСТЬ: M (4-6 часов для SQLite через better-sqlite3).
РИСК ЕСЛИ НЕ ДЕЛАТЬ: массовый negative-feedback при первом же
рестарте под нагрузкой; невозможно горизонтально масштабировать.
Файлы: `lib/session.ts:25`

#### finding-018 [P0]: Нет CSRF-защиты на изменяющих эндпоинтах

ЧТО НАШЁЛ: все POST-роуты в `app/api/ai/*` принимают запрос только
по session_id из cookie, без CSRF-токена.
ПОЧЕМУ ВАЖНО: атакующий может с другого сайта триггерить вызовы
OpenAI на счёт пользователя (счёт растёт) или мутировать состояние
сессии. Sample-роут вообще GET — создаёт сессию по клику на ссылку.
СЕЙЧАС: ноль CSRF-проверок.
ПОТОМ: CSRF-токен в header `X-CSRF-Token` для всех state-changing
запросов; double-submit cookie pattern.
СЛОЖНОСТЬ: M (3-4 часа).
РИСК ЕСЛИ НЕ ДЕЛАТЬ: при любом росте популярности — реальный вектор
атаки и потенциальные счета за OpenAI.
Файлы: все `app/api/ai/*/route.ts`, `app/api/sample/route.ts:275`

СЛОЖНОСТЬ: S (1-2 часа, потенциально мажорный bump).

### 5. Производительность и observability (4 находки: P0=0, P1=3, P2=1, P3=0)
